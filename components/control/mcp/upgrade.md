# Upgrade — MCP tool surface

Nothing infrastructure-grade upgrades itself: a pin moves on a branch that carries a reason and a
rollback line, the candidate is seen running against its real consumer (**the platform API it calls**)
before the PR merges, and the merge authorises promotion rather than closing this item.

**No image has ever been built, started, upgraded or rolled back from this directory, and no rehearsal
exists.** `versions.json` says `verified_on: null` and `image.identity: null` for that reason. Everything
below is a recipe. The first real version move is the one that writes the first row of results here, and
until then nobody should read any line of this file as a tested path.

## 1. What a pin move actually touches

| Layer | What changes | Who else feels it |
| :-- | :-- | :-- |
| the SDK pin `mcp==1.29.1` | `components/control/mcp/requirements.in` **and** `[project.optional-dependencies] mcp` in `pyproject.toml`, which are the same version spoken in two files | the MCP *test tier*, which runs against the extra as installed in the test environment, and `tests/test_mcp_component.py`, which refuses the two pins drifting. A different SDK minor can move the wire protocol (`mcp.types`, the `tools/list` schema, the stateless HTTP shape) that `local_observe/platform/mcp.py` is written against — that module is in the same change or the change is not finished |
| the rest of the lock | pydantic, pydantic-core, httpx, starlette, sse-starlette, cryptography and the other 20 names are the SDK's closure, not this project's choices | nobody imports them directly. `local_observe/` imports stdlib, PyYAML and jsonschema; a lock move that changes *those three* versions is a platform-image change wearing a MCP costume — check it against `components/control/platform/requirements.lock` (§2) |
| the base interpreter `library/python@sha256:9c47360a…` | `ARG LO_PYTHON_IMAGE` in `Dockerfile` **and** `python_base` in `components/control/platform/versions.json`, which is where the same digest is recorded | one pin, two images. A move here moves both or is documented as a deliberate split, and `tests/test_mcp_component.py` fails a Dockerfile base digest that differs from the platform's |
| the product source | the whole `local_observe` tree is `COPY`d in, exactly as the platform image does | a source revision that moves `tools.py`'s registry or `mcp.py`'s transport moves this image too, and the exposed tool count moves with it (`CONTRACT.md` §5). There is no versioned API between the two halves: they are one tree |
| the platform endpoint's contract | `/v1/actions`' request and answer shape, `/v1/records`, `/v1/me`, the role gate's refusal codes | `tools.propose_tool` (which forwards only the platform's stable `error` code) and the refusal matrix in `tests/test_platform_tools.py::ActionPairTests`. A platform that answers no `action_id` is a `Proposal refused by the platform: <code>`, which is a refusal and not a partial success |
| the surface's shape | `structuredContent` was **removed** by mcp tool surface: an answer is now `content[0]` (the document) plus `content[1]` (`{"provenance": …}`) | the operator's **MCP client**, not this repository. A client that read `structuredContent` reads `content[0]` now. This is the one breaking change in the surface's recent history and it is a consumer's upgrade, not a redeploy |

## 2. Regenerating the lock

`docs/BUILD.md` carries the `pip download` recipe for the other two locks and it does not work for this
one on a Windows host: `mcp` declares `pywin32; sys_platform == "win32"`, and pip evaluates a
requirement's marker against the interpreter it is *running*, not the `--platform` it was handed, so the
resolver asks PyPI for pywin32 and refuses. The lock header names the command that does work —
`uv pip compile … --python-version 3.12 --python-platform x86_64-unknown-linux-gnu --only-binary :all:
--generate-hashes` — the same tool `components/control/sigma/compiler.lock` was generated by.

Then three checks, in this order, none of which is optional:

1. **Trim** to the wheels a `python:3.12-slim` linux/amd64 interpreter can select: `cp312` wheels, `abi3`
   wheels whose stated minimum is at or below cp312, and `any`-platform wheels. Drop every sdist — with a
   source hash in the lock, `--require-hashes` would let the build stage *compile* a package nobody
   reviewed instead of failing. Where a project ships several glibc levels, keep each x86_64 linux wheel:
   pip chooses among them by tag priority, and a single hash naming the wrong variant fails the build.
2. **Re-hash from the bytes**: download each named file and recompute its sha256 against PyPI's declared
   digest (row 15 of `conformance.md`). Do not paste hashes from a resolver's own output as though they
   were observations.
3. **Compare with the platform lock**: the ten packages the two share must agree on version, and every
   platform digest must be among the hashes here. If they do not agree, either the base pin moved under
   one image or a resolution picked a different build — and a host running two images with two uvicorn
   versions is a debugging session waiting to be misdiagnosed.

Row 1 of `conformance.md` (the build itself, `pip install --require-hashes` on linux/amd64) is the check
none of those three can substitute for, and it has never run.

## 3. Ordering, and what out-of-step versions do

1. Land the pin change on a branch, with the reason and the rollback line, and the MCP tier green
   (`requirements-dev.txt` in a separate environment; the tier must **run**, not skip —
   `docs/testing-standards.md`).
2. Build the candidate image, tag it `:candidate`, and record its config ID **plus the source revision**
   it came from in `versions.json` — but do not edit the live environment yet.
3. See it running against its real consumer before merging: start it in a throwaway project (`-p
   lo-mcp-upgrade`, a port that is not the live one) pointed at a **scratch** platform, and run rows 3-7 of
   `conformance.md`. If the change touches `/v1/actions` semantics, the platform side gets its own
   rehearsal in `components/control/platform/upgrade.md`, not a ride on this one.
4. Promote by re-pointing `LO_MCP_IMAGE` at the candidate's config ID. `pull_policy: never` means the tag
   is decoration — the value is the ID, and a wrong one is a start failure rather than a silent fetch.
5. Restart order: platform first if the platform is also changing (this surface reads it and holds nothing
   of its own), then this service. An MCP service talking to an old platform is a set of refusals, not
   corruption; the reverse (a new platform, an old surface) is the same.

**What a mismatch does *not* do:** there is no schema, no migration and no persisted shape in this
container, so no version pair here can corrupt state. The worst case is that a tool call is refused, or
that an answer's two content blocks are shaped differently than a client expected (§1, last row).

## 4. Rollback line

Unusually short, and that is the component's one real upgrade virtue:

```
LO_MCP_IMAGE=<the previous local config ID, if the host still holds it>   # else rebuild the old revision
docker compose -f components/control/mcp/compose.yaml --env-file <private env> up -d --force-recreate mcp
```

Nothing is restored, unwound or reconciled, because nothing was written. Two honest caveats: the old ID
only exists if that image was never pruned and was built **on this host** (a config ID is not a registry
digest and does not travel), and the map is *not* rolled back with the image — if the candidate added or
rotated an agent row, reverting the image leaves those credentials in place and still valid, which is the
direction that matters: identity is the operator's state, not this container's.

## 5. Re-run after any move

Rows 1-11 of `conformance.md`, in order (row 1 first: a lock that cannot install is not a candidate).
Then the MCP test tier, and the base tier, and `python -B scripts/check_foundation.py`. Re-check the
resource limits against the pinned build rather than trusting them: 256 MiB was copied from the platform
manifest as a bound, pydantic's import cost is unmeasured here, and an OOM-kill during import reads as a
crash loop and not as a memory setting. Record what was seen, with a date, in this file — a pin move whose
only evidence is a merged PR is a pin move nobody can repeat.
