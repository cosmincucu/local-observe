# Unit: durable refusal audit (`platform/refusals.py` + the `Store.refusal` boundary)

## Purpose

A refused action attempt must be *durable* — readable after the process that made it is gone, by an operator who was not watching. Before this unit a refusal left nothing: `state.py` raised before reaching its own `audit(...)` call and `api.py` answered a `StateError` with a 400 it did not log, so nine refused bad actions looked like nobody had tried. What ships is one append-only `action.refused` row per refusal — a fixed attempt word and a fixed reason word — under a rate bound, **per refusal the budget let through and the identity it may name**: over quota the row is `dropped`, a failed write is `failed`, an unverifiable identity is `unauditable`, and each still refuses and moves only a counter. The asynchronous audit writer added a fourth case belonging to the transport's route alone: on the `summary` 403 the write may never be *attempted*, because the app holds one audit slot and it is busy or closing — either shed moves `overloaded`, `closed` says whether admission had been shut for shutdown (a boolean, not a tally of sheds), and a shed spends no budget token. None of this changes a decision: the refusal, its status, its sentence and every action/incident/execution row are what they were.

## What is audited, and what is not

Four `Store` methods are wrapped whole — role gate, bounded validations and the injected `policy()` call inside:

| method | `attempt` word | durable subject |
|---|---|---|
| `propose_action` | `propose` | `unbound` (a refused proposal has no row to point at) |
| `decide` | `decide` | the `action_id`, when it is a canonical UUID |
| `claim_action` | `claim` | the `action_id`, when it is a canonical UUID |
| `execution_outcome` | `outcome` | the `execution_id`, when it is a canonical UUID |

Plus the one refusal the transport makes for itself: a `summary` credential POSTing to exactly those four routes is turned away before any `Store` method is entered, so the edge records the row (reason `summary-only`, subject `unbound`, identity from the bearer credential) — since #135 on the app's one-slot dispatcher rather than on the serving loop, with what it records and the gate deciding it untouched. The role gate runs *after bearer authentication*, before the first `receive()`, so it outranks the body parser, size and shape checks: a `summary` credential sending `b'{broken'` or 70 000 bytes gets the same audited `403 summary_only` as one sending well-formed JSON, and no branch parses a body to decide whether that audit happens (`test_the_summary_gate_answers_a_refusal_before_the_body_is_read`). Invalid authentication stays a `401` with no audit row.

**Not audited, deliberately:** `record_callback` and every notification refusal (the boundary is the action lifecycle, a callback is an intent rather than a decision, and its refusals return `None` instead of raising — pinned by `test_the_callback_route_is_not_a_refusal_audit_subject_in_this_scope` so nobody reads it as covered); `intake`, `put_evidence`, `records`, the notification retry/reset/mode methods and `expire_actions`; anything that is not a platform refusal class, since a `KeyError` from a broken action table is a server bug and stays a logged 500; and anything the parser, size, shape or authentication gates answer, or any unknown route — those stay write-free, asserted by counting `sqlite3.connect` calls rather than by noticing an absent row, so an attacker with no valid bearer token cannot grow the operational database and a malformed body never reaches a writer. The cost is stated, not hidden: credential guessing stays invisible here and belongs to the edge.

## The ordering, which is the whole design

```python
def decide(self, action_id, decision, actor, *, now=None):
    with self.refusal('decide', actor, action_id, now=now):   # catches, audits after the rollback
        require(actor, 'human')                               # gates and validations are inside
        ...
        with self.transaction() as connection: ...
```

`Store.transaction()` is `closing(connect())` around `with connection:`, so a raising body is rolled back and its connection closed *on the way out of the inner `with`* — before the exception reaches `refusal()`, and the audit insert runs in its own fresh `BEGIN IMMEDIATE` after the failed one is gone. Three consequences, each pinned by a test: the refused partial state cannot be committed by the audit write, because it was already discarded (`test_the_refused_partial_state_is_gone_before_the_audit_row_is_committed`); the audit row cannot be erased by that rollback, because it was never in it; and there is no second SQLite writer, because the audit uses the same `Store.transaction()` path with `Store.record_refusal` as its only entry point. Lifecycle methods still audit inline in the refused call; since #135 the `summary`-route write runs on whichever thread the dispatcher handed the job to, so that one row is serialised against other writes by SQLite's own writer lock and busy timeout rather than by thread identity — the app guarantees it never holds two of those writes in flight, not that they share a thread. Nesting is also pinned structurally: an AST test asserts the wrapper is each audited method's first statement, that every `self.transaction()` sits inside it, and that `self.audit` is never called from an `except` block. A decorator, ~33 per-`raise` `try/except` sites and one-transaction savepoints were all rejected (signature-guessed subjects; future `raise`s escaping the audit; widening the shared `Store.transaction()` API is outside this card). The cost is the crash window: a process killed between the rollback and the audit commit loses that one refusal row and no state whatsoever, so this is ordinary SQLite commit durability, not a promise that every refusal is recorded.

## What a row may contain

Five existing columns, no new table, no schema move (`VERSION` stays 3):

| column | bound |
|---|---|
| `at` | the refused method's resolved instant; a `now` the module cannot format is ignored for the real clock |
| `actor` | `Actor.identity` only when it satisfies `state.label()` (`[a-zA-Z0-9_.:-]{1,128}`) and the role is one of the six |
| `operation` | the literal `action.refused` |
| `subject` | a canonical UUID, or the fixed sentinel `unbound` |
| `detail` | `{"attempt": …, "reason": …, "role": …}` — three words, each from a closed set |

The widest legal row's stored text is measured and pinned at ≤ 512 bytes (`refusals.ROW_TEXT_LIMIT`), so a future field cannot quietly widen it. Never in any field: a request body or any field of it, a bearer/runner/callback token or a digest of one, a URL, an endpoint, a path, a channel name from a URL segment, an exception message (the mapped word is stored, the sentence never is), an identity read out of a body, or a derived hash. **Invalid identity ⇒ no row at all:** not an `Actor`, an identity that is not a bounded label, a role outside the six, or an `attempt`/`reason` that is not a string in the closed vocabulary yields `unauditable` and no write — `refusal_row` type-tests before consulting those sets, so a `list` reason is unauditable rather than a `TypeError` where a denial should have been — and fabricating an actor field, hashed or truncated or named `unknown-caller`, would put words in a reader's mouth about who was refused. **Direct `Store` callers are trusted attribution, not authentication proof:** the HTTP identity is trustworthy because `secrets.compare_digest` against the configured credential file decided it, while at the direct-`Store` edge (CLI, workers, tests) the row records *who this process was told was calling* and is never evidence of authentication.

## The reason vocabulary

`refusals.SENTENCES` maps a **whole** platform sentence to one word by exact match — exact, not substring like `api.stable_code`: an error body is transient and may be imprecise, a durable record may not be steerable by text a caller influences. An unseen sentence becomes `unclassified`, one fixed word with no echo, reachable in practice only from a deployment-supplied policy closure that raises its own text. Two tests keep the map honest both ways: every literal `raise StateError(...)`/`raise InvalidInventory(...)` inside the four audited methods, inside the shared `require`/`label`/`identifier` gates and inside `policy.py` must be in the map, and every declared word and attempt word must be provokable. `attempt` exists because one sentence (`Action is not pending`) is reachable from two stages; the pair is what an operator reads.

## The write budget, and what it does not bound

`refusals.RefusalAudit` is a token bucket: capacity 64, initially full, refilled at 1 token/second from `time.monotonic` — never the `now=` a `Store` method accepts, since a rate limit an attacker sets is not a limit. It is created per `Store` object, so per process, and its lock is never held across the SQLite write (`reserve()` and `count()` are separate calls so the transaction runs between them). It is **one of two budgets, never merged into one number**: the bucket bounds how fast rows may be *written*, the dispatcher below bounds how many of the transport's writes may be *attempted at once*, and `Store.record_refusal` stays the only writer, classifier and counter owner. So a flood has two shapes: a refusal inside a lifecycle method still audits inline, and 64 concurrent ones can spend the whole burst before about one row per second; a `summary` 403 is bounded by the one slot, whose parked callable sheds what arrives while it runs, so a burst's rows are capped without being fixed by its request count. Reaching the bucket's 64 tokens that way needs 64 admitted refusals arriving one after another — and an attempt is not a row (the invariant file's nine attempts are that sequential shape and fit inside the burst three times over). `GET /v1/runtime` reports the bucket as a pure in-memory read, taking no connection, and `Store.status()` is **not** widened (its exact dict is pinned by `tests/test_regression_schema_version.py`):

```json
"refusal_audit": {"written": 1, "dropped": 0, "failed": 0, "unauditable": 0,
                  "capacity": 64, "refill_tokens_per_second": 1, "tokens_available": 63,
                  "scope": "process-local", "resets_on_restart": true, "saturated": []}
```

**What this bounds is the rate, not the history.** A restart resets counters and bucket while committed rows stay in `audit` permanently, so a process restarting N times can accumulate N × 64 burst rows. `dropped`, `failed` and `unauditable` are volatile: read after a restart they say zero, not "nothing happened". Nothing prunes `audit` — its `BEFORE UPDATE`/`BEFORE DELETE` triggers make pruning a schema change and retention is not this card's to touch — so sustained refusal traffic writes at 1 bounded row per second forever. A burst also crowds the bounded read view without deleting anything: `GET /v1/records/audit` is newest-first, hard-capped at 100 rows with no offset, so 64 refusal rows can push real transitions, claims and deliveries out of the window an operator reads by default. That legacy window is unchanged and still nobody's to widen quietly — the paged audit reader added a **second** read rather than loosening that one: `GET /v1/audit` walks the same table in bounded pages (`docs/units/audit-reader.md`), and reaches the rows behind a burst without moving the capped window by a byte. The new read answers `category=action-transitions` from a closed set of eight **completed** transitions that does *not* include `action.refused`, so a refusal is never mistaken for a transition on the way to answering "what actually happened?". The rollback-to-commit loss window is real, a failed write spends its token rather than being retried (a locked database costs refusals, not a retry storm), and a shed refusal is a third way to lose a row: app-local, never attempted, no token spent, counted in `overloaded`. This is therefore **not a complete durable history of refusals under overflow, failure or contention** but a bounded, observable record — which is why **a `403` is not proof of a durable row** and why the two counter sets, never the status code, say whether a refusal was written, dropped, failed, unauditable, or never dispatched. Counters saturate at signed-63 (`refusals.COUNTER_LIMIT` = 2**63-1, not the bucket's 64) and name themselves in `saturated` rather than wrapping or lying about a total, in both sets; a state field (`capacity`, `in_flight`, `closed`) can never appear there. There is no per-actor cache (a flood of distinct subjects adds no keys — asserted), no `SELECT` on the audit table in the refusal path, no second database, and nothing that decides anything reads refusal rows: the audit table is a record, never an authorization input.

## Failure and log volume

An audit failure may not upgrade, replace or echo the refusal it was recording. `record_refusal` raises nothing back into the denial for the caller inputs this path supports (strings from the closed vocabularies or anything outside them, an `Actor` or a non-`Actor`, any subject) and the persistence failures it handles below; it does not promise that an object with a throwing `__eq__`, or a broken injected clock or logger, cannot propagate. `refusal()` re-raises the original exception unchanged, so the client gets the same 400 and the same fixed sentence and `store.status()` does not move. A failed write increments `failed` and logs **one** line — `Refusal audit write failed`, carrying only the exception class — at most once per `FAILURE_LOG_INTERVAL_SECONDS` (60) of **actual elapsed** monotonic time, measured from the line really printed rather than an aligned minute bucket (two failures 0.1 s apart cannot print twice) and read inside the accounting lock (a stale sample cannot reorder between threads). The success path logs nothing: the durable row is the record, and a line per refusal would double the flood surface. No traceback, body or driver message reaches the log or the row.

## The summary 403's write, off the serving loop

**Why, measured once.** `GET /v1/runtime` reads no database, yet a refusal it was not involved in could hold the loop that serves it: that 403 audited itself inline, an audit write is a `BEGIN IMMEDIATE`, and with the write lock held by another thread on the same file the handler waited inside the statement on the existing 10 s busy timeout while a concurrent memory-only runtime read waited behind it — reproduced on this card's base with a reviewer-only probe that has to give its own lock-holder a 2-second safety release before the loop answers. A read-only role's write was a way to stall a health endpoint.

**Scope, exactly.** The four `summary` POST refusals named by `REFUSAL_POST_ROUTES`, and nothing else. The four `Store` lifecycle methods' audits stay inline and every other database read stays synchronous — deferred by decision, not an oversight: a locked database still stalls a refused `decide`, and the loop with it. The delivery loop's own writes are *not* newly offloaded here: its `expire_actions` / `deliver_one` calls already ran off the serving loop before #135, and what this change touches is only how their cancellation and completion are tracked, so releasing the state-file owner lock can never outrun a live write. `GET /v1/runtime` keeps every field and its memory-only behaviour and gains exactly one key, `refusal_audit_dispatch`, fixing no other contention. No new role, route, schema version, environment value, dependency, mount, token or `Store` change appears and `Store.status()` is unchanged. `refusal_dispatch.py` holds `RefusalAuditDispatcher` (`submit`, `close`, `wait`, `wait_idle`, `status`, `current_job`, `in_flight`, `closed`; constants `CAPACITY`, `SCOPE`, `RESETS_ON_RESTART`, `COUNTERS`), `api.py`'s `audit_summary_refusal` is its only caller, and the admitted job is a `DispatchJob`.

```json
"refusal_audit_dispatch": {"capacity": 1, "in_flight": 0, "admitted": 1, "overloaded": 0,
                           "failed": 0, "closed": false, "scope": "app-local",
                           "resets_on_restart": true, "saturated": []}
```

`capacity` is always 1 — one submitted-or-running audit callable per `create_app` instance, no waiting queue, no semaphore waiter — `in_flight` is 0 or 1, and `closed` is `false` while admission is open and `true` once lifespan shutdown has shut it: **states, not tallies**. `admitted`, `overloaded` and `failed` are the three names in `refusal_dispatch.COUNTERS`, the only fields `saturated` can ever list, saturating at `refusals.COUNTER_LIMIT` under a lock because the accounting is cross-thread. `scope` is `app-local`, narrower than the bucket's `process-local`: two apps over one `Store` have two slots and two tallies, neither a sum of the other. `resets_on_restart` is `true`, and `failed` counts **unexpected dispatcher submission or call failures only** — a Store failure `record_refusal` already handles stays in `refusal_audit`'s counters, because the two surfaces answer different questions.

1. **Fail-fast, never queued; a shed spends nothing.** A refusal arriving while the slot is busy, or after shutdown closed admission, gets the byte-identical `403 summary_only` immediately from a body that is still never read, and moves `overloaded` once: busy and closing are one answer at the gate and `closed` tells them apart afterwards. No bucket token is spent and none of the four `refusal_audit` counters moves — calling an unattempted write `dropped` ("tried, over quota") would be a false statement about a write that never happened. Concurrency can lose rows and how many is not a property of the request count; that is the price of not stacking unbounded writes behind a locked database, and it is counted rather than hidden.
2. **An admitted request still waits for its own attempt.** Admission is nonblocking, the response is not: the `403` goes out only after that request's one audit attempt completed — synchronously inside the callable, never on the serving loop, never an early return with the work abandoned. Whether it left a row is still the rest of the `Store` contract (a valid `Actor`, quota, a commit that succeeded); where those fail, `dropped`/`failed`/`unauditable` explains the absence.
3. **Cancelling a request cancels neither the write nor the slot.** The future a request awaits is a notification (`loop.create_future()`) never chained to the submitted work, and the future `run_in_executor` returns stays private to the module — that privacy is what makes "no cancellation path reaches the callable" a property rather than a convention. Capacity is released only by the callable's own thread, in a `finally` after the SQL returned, so the next refusal stays shed until the write is genuinely over, and the wait survives a loop other than the submitting one. A notification reporting `cancelled` is a lost wake-up, not proof that work ended. If an external teardown drops a *queued* submission the gate stays fail-closed — slot occupied, `failed` counted — because releasing capacity on a cancelled state is the inference this module exists to refuse; that is fail-closed accounting, not a promise of bounded shutdown around a hostile teardown.
4. **Shutdown drains the real work before the owner lock goes.** Cleanup closes admission, waits for the admitted audit callable **and** the delivery loop's blocking `expire_actions` / `deliver_one` call to end, releases the exclusive state-file owner lock, and sends `shutdown.complete` **only** on a normal, error-free, uncancelled shutdown. A failing startup, a `receive()` that stops delivering the shutdown message, a `send()` that cannot deliver it, or a repeated cancellation still drains, then propagates that original failure or cancellation instead of a false `complete`. The delivery-call wait remembers a cancellation landing mid-call until the callable's own thread sets its event; a cancelled execution wrapper is never proof the work stopped. An external teardown dropping a *queued* submission can leave that wait fail-closed: `busy_timeout` bounds the driver's retries, not a thread, so no hard timeout, extra ASGI message type, deadline or promise against process death stands in for it.
5. **Without a lifespan it works, and leaks nothing.** Driving the ASGI app directly is a legitimate caller, not a degraded one: the write still leaves the loop, there is no inline fallback for that path and no per-app thread left idle — submission goes to the serving loop's **default executor**, acceptable only because admission bounds it at one outstanding callable where an unbounded executor queue would not be.
6. **A job holds nothing the caller controls:** the fixed attempt word already in `REFUSAL_POST_ROUTES`, the `Actor` the bearer credential decided and the fixed `summary-only` reason, closed over the single `Store.record_refusal` call — no body, bearer token, subject, URL, path, exception message, caller `now=` or other caller-controlled field. The dispatcher imports no `Store`, opens no connection, never reclassifies a sentence, reimplements a row or patches that classifier from outside.
7. **A dispatcher failure stays quiet:** `failed` moves and one line names the exception class only, with no payload and no traceback, at most once per 60 seconds of actual elapsed monotonic time, never on a success path and never per shed; it cannot change the status, body or durable record of the refusal it failed to help.

## Reading the rows

`GET /v1/records/audit` serves them to a reader token **newest first**, like every other record read (`Store.records` is `ORDER BY rowid DESC LIMIT ?`, capped at 100, no offset), with no new route and no new field on that route; that cap is why the burst-crowding note above belongs to the read surface rather than to the file. Since the paged audit reader there is a second reader of the same rows — `GET /v1/audit`, the bounded paged walk in `platform/audit_reader.py` ([its unit contract](audit-reader.md)) — which reaches older rows past the 100-row window and shows them under `category=all` only, because a refusal is a denial and not a completed transition; it changes nothing about the legacy route, and neither read may be used as an authorization input. `presentation.records` parses `payload` for other tables only, so the row renders as stored. `Store.backup()` and `deployment/state_copy.py::copy_state` copy `audit` with the rest of the file: no new backup mechanism, no backup-matrix row, no retention tier — `AGENTS.md`'s backup directive still applies to the repository change itself, and the paged read inherits the same copy because it reads the same table.

## Gotchas / debt

* `refusals.py` imports `state.py` at module level and `state.py` imports `refusals` from *inside* its functions (the `notification_safety` precedent); inverting that is an `ImportError` at service start, and `test_the_wrapper_covers_exactly_the_four_audited_methods` keeps the surface small. A wrapped method's body sits four spaces deeper than it was — read the wrapper as the boundary; the AST test makes "forgot it" loud.
* Wrapping a fifth method moves `refusals.ATTEMPTS`, `AUDITED_METHOD_NAMES`, the table above and `DEPENDENCIES.md`'s refusal row together. A new transport-stage reason word must stay **out** of `refusals.REASONS`: that disjointness *is* the duplicate-row firewall, standing in for a per-request "already audited?" flag a future handler could forget, which is why `api.py`'s `StateError` branch stays write-free.
* Contention with the delivery loop, which writes from executor threads, is the platform's existing single-writer contention: a refusal's `BEGIN IMMEDIATE` can wait on the 10 s busy timeout and a timeout lands in `failed`, not in a partial commit.
* Moving only the summary route is a decision, not an oversight: that route is still a database writer, an admitted `summary` denial still costs a bucket token and one real attempt, and the four lifecycle refusals still audit inline on the loop, so the stall #135 removed from the summary route stays reachable from a refused `decide`.
* The dispatcher's counters are as volatile as the bucket's and narrower (one app instance, one process), and a `capacity: 1` read from `/v1/runtime` is a snapshot of a moving slot: what the next concurrent refusal will meet, not what the last one did.
* Still open after this unit: bearer-token guessing at the edge (front-door rate limiting is unowned) and the notification/intake/evidence refusals named above.
